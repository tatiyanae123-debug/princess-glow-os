# Glow OS — Continuous World Master Experience Layer

**Status:** Current master page-experience specification, September 2, 2026.  
**Authority:** This layer is subordinate to and compatible with the existing Glow OS constitution. It strengthens how rooms express the system. It does not erase data, workflows, provenance, safety, approval, accessibility, or the five-world foundation.

## Constitutional foundation

Glow OS is one continuous living world. Technical routes are addresses and state changes, not visual page replacements.

The five primary worlds are permanently:

1. Today
2. Plan
3. Life
4. Brain
5. Create

No Life subsystem, utility, database, or temporary workflow may become a sixth primary world.

## Shared Glow language

All rooms remain visibly part of one system through:

- Living Glow Aura as embedded intelligence, never a chatbot orb, mascot, fairy, person, or literal angel.
- Glow Matter as responsive liquid-crystal / pearl / polished-stone material behavior.
- Ivory pearl, polished stone, champagne metal, restrained water reflection, natural refraction, refined typography, and Apple-level restraint.
- Permanent Ask Glow, consistent gestures, save/undo/search/action receipts, contextual voice, and target-travel feedback.
- iPhone and iPad-first usability with desktop support.
- Reduced-motion support and dyslexia-friendly presentation controls.
- Non-shaming health, body, money, productivity, and relationship behavior.
- No false actions, silent destructive changes, or unapproved consequential rearrangements.

## The room law

Every important Glow room must be differentiated across these dimensions:

**climate → space → physics → intelligence → information → controls → completion → sound → Aura behavior**

A room is incomplete if it is merely a recolored template.

## Anti-repetition QA

Every finished screen must pass all of these questions:

- Different dominant spatial metaphor?
- Signature interaction?
- Unique light climate?
- Meaningful motion model?
- Different completion behavior?
- Distinct Glow role?
- Different information exploration?
- One primary human question?
- Navigation still feels like Glow?
- Avoids copied card structures?

## World definitions

### Today — Living Center

Today represents the present. Its spatial law is temporal depth:

**Now → Next → Later → Tonight → Tomorrow**

Now has maximum clarity. Future layers become smaller, softer, lower contrast, farther away, and less demanding. Completed time leaves warm residual light rather than becoming another checkbox grid.

Today must never regress into a conventional widget dashboard.

### Plan — Time Observatory

Plan is spatial time, not a bundle of calendar/task/project apps. Today is physically closest; tomorrow is nearby; distant time recedes. Deadlines become landmarks, projects occupy temporal territory, and Glow can project conflicts, preparation shadows, protected time, alternatives, and future-self scenarios.

Planning remains non-destructive. Glow may simulate and propose. Nothing becomes real until approved.

### Life — Personal House

Life contains lived domains, each with its own habitat and physical behavior. Beauty, Body, Fitness, Wellness, Food, Closet, Home, Money, Work, Relationships, Travel, and other domains are rooms in Life, never replacements for the five-world structure.

### Brain — Depth World

Brain must never become Notion. Notes = desk, Notes Web = constellation, Memory = cinema, Thoughts = floating holding field, Ideas = incubation, Insights = observatory, Timeline = river, Decision Archive = crossroads, and Brain Graph = universe-scale relational exploration.

### Create — Mist to Structure

Create is not a collection of AI tools. Its governing transformation is:

**vague → legible → structured → tangible**

Capture accepts input before classification. Creative Studio lets the active medium dominate. Inbox is temporary and visibly routes objects toward destinations. Import exposes source, extraction, proposed meaning, duplicate/conflict state, destination, and approval.

# Reference Image Constitution — Permanent

## Core law

**The reference photo is not inspiration. It is the room. Glow must make that exact world become the live interface.**

The user does not want a conventional interface laid on top of an image. The image defines the room's physical world. Glow must understand that world, preserve it, and convert its architecture into the functioning interface.

The governing equation is:

**Reference image = visual blueprint**  
**Glow architecture = interactive structure**  
**Live data = information inhabiting that structure**

Visual fidelity and functionality are not competing goals. Every approved Glow page must do both at once:

**look almost exactly like the approved reference + behave like a real responsive, living, three-dimensional operating system.**

## Reference image authority

Any reference image the user explicitly approves or sends as the target for a Glow page becomes the authoritative visual blueprint for that page until the user explicitly replaces it.

“Match the reference” means preserve, as closely as technically possible:

- composition
- camera position
- camera height
- camera angle
- crop
- spatial layout
- architectural forms
- object placement
- object scale
- depth relationships
- foreground / middle-ground / background hierarchy
- material character
- surface reflectivity
- lighting direction
- light intensity hierarchy
- atmosphere
- color relationships
- negative space
- focal points
- visual balance
- horizon placement
- environmental density
- where information appears
- where the eye should land first
- emotional character of the room

The first frame of the live implementation should be immediately recognizable as the approved reference.

Reference fidelity must never be achieved by flattening the page into a static screenshot. The room must remain live, responsive, accessible, data-driven, and interactive.

## Do not put UI on the world. Turn the world into the UI.

Glow must never be implemented as:

**beautiful background image + absolutely positioned HTML cards + generic controls**

Instead the implementation order is:

**understand room → identify physical structures → assign semantic meaning → assign information → define interaction → define state response → define completion → implement geometry**

Architecture determines information placement. Information is not positioned first and decorated afterward.

## Environment semantic map — required before implementation

Before live text or controls are placed on any user-supplied Glow reference image, create an internal semantic map of the scene.

For every meaningful object, determine:

1. What is this physical object?
2. Why is it present in this room?
3. Is it decorative, atmospheric, navigational, informational, interactive, state-bearing, or mixed?
4. What concept naturally belongs to this object?
5. What exact live information belongs here?
6. What information must not live here?
7. How much information can physically fit without damaging the reference?
8. What is the object's usable information face?
9. What are its safe content boundaries?
10. What perspective and curvature does the content need to inherit?
11. What is the object's material behavior?
12. How does the user know it is interactive?
13. Where can the user tap, click, focus, swipe, drag, or speak?
14. What happens when interaction begins?
15. What happens when more detail is requested?
16. Does the object deepen, unfold, illuminate, rotate, expand, move closer, reveal another layer, or transition elsewhere?
17. What does completion look like physically?
18. What does loading look like?
19. What does an empty state look like?
20. What does a disabled or unavailable state look like?
21. What does an error or warning look like without breaking the room?
22. What role does the Living Glow Aura play around this object?
23. Does this object need spoken guidance?
24. What happens under reduced motion?
25. How does this object recompose on iPhone portrait, iPad portrait, iPad landscape, and desktop?

No page is complete until this semantic mapping has been resolved.

## Object → meaning → information → interaction → response

Every meaningful interactive Glow structure should follow this relationship:

**object → meaning → information → interaction → response**

Never:

**background image → floating UI layer**

Examples:

- A monument can house priorities.
- A temporal aperture can house the next event or open time.
- A basin or vessel can embody capacity.
- A pathway can express the flow of the day without needing paragraphs.
- A mirror can become the Makeup workspace.
- A rail can become the Closet organization plane.
- A shelf can hold actual owned products.
- A horizon can embody future time.
- A desk can become Notes.
- A river can become Timeline.
- A constellation can become Notes Web or Brain Graph.
- A cooking surface can become the current recipe step.

The object should communicate the information category before the user even reads the words.

## Surface geometry law

Every information-bearing architectural surface must be treated as a real spatial plane, not a loose bounding box.

For each surface define:

- exact usable polygon or mask
- local coordinate space
- inner safe margin
- optical padding
- transform origin
- perspective
- skew
- rotation
- curvature approximation if needed
- maximum text width
- maximum text height
- maximum line count
- type scale range
- line-height range
- hierarchy rules
- overflow behavior
- contrast treatment
- touch region
- focus treatment
- expansion origin

Text and controls must remain inside the object's usable face.

They must respect:

- curvature
- camera perspective
- physical depth
- edge boundaries
- lighting
- reflections
- local material
- viewing angle

Nothing should look as though it is floating one centimeter in front of the object unless intentional suspension is part of that room's physics.

## Typography belongs to the object

Typography is not a global overlay layer.

Text must inherit the physical logic of the surface it inhabits.

Possible treatments include:

- etched
- engraved
- illuminated from within
- softly projected
- inlaid
- suspended in Glow Matter
- reflected
- printed on a physical material
- embossed
- carved
- written on paper or glass-like matter where contextually appropriate

The text must still remain legible and accessible.

If a live title is too long for the physical surface:

1. preserve the full underlying data
2. adapt the display treatment
3. shorten presentation only where semantically safe
4. change hierarchy before changing architecture
5. reveal the full title in the natural expanded state

Do not destroy the approved composition merely to fit a database label.

Long text must never be allowed to wrap randomly across a beautiful architectural object.

## Controls must also inhabit the architecture

Icons, toggles, completion controls, indicators, handles, and arrows must feel physically related to their host object.

They may appear as:

- inset pearls
- small engraved controls
- luminous touch points
- illuminated seams
- material deformations
- embedded symbols
- subtle handles
- edge illumination
- responsive apertures

They must not resemble generic floating mobile buttons unless the approved reference explicitly calls for that behavior.

Tap targets may extend invisibly beyond the visible control for usability, but the visible control must remain integrated with the object's geometry.

## Expansion must originate from the object

When a user asks for more detail, Glow should preserve spatial continuity.

Prefer:

- object deepens
- object opens
- object unfolds
- camera moves closer
- interior layer becomes visible
- surrounding room dims while the originating object remains spatially anchored
- Glow Matter stretches into a larger working surface

Avoid unrelated centered modals and generic bottom sheets unless accessibility or device constraints make a spatial alternative inappropriate.

The user should always understand where expanded information came from.

## Completion must transform the object

Completion behavior should not be reduced to a checkbox state.

The originating object should respond according to its room physics.

Examples:

- a completed Today task leaves warm residual inscription/light
- a finished recipe step settles behind the active step
- a completed workout movement releases grounded rhythmic light
- an approved Plan change seals into the time structure
- an imported object visibly travels toward its destination

Completion should communicate meaning, not decoration.

## Not every object becomes UI

Glow must preserve architectural restraint.

Some elements are:

- pure atmosphere
- orientation
- visual breathing room
- light sources
- depth cues
- emotional anchors
- environmental storytelling

Do not convert every table, flower, window, wall, column, reflection, shelf, chair, decorative arch, vessel, or object into an interactive surface merely because space is available.

A believable world requires inactive architecture too.

## Today-specific canonical mapping example

When the approved Today reference includes these structures, treat them semantically rather than as backdrop:

### Priority monument

**Meaning:** active commitments that matter now  
**Information:** highest-relevance priorities  
**Interaction:** touch row to enter; embedded pearl/control to complete  
**Expansion:** monument deepens or opens  
**Completion:** row resolves into warm residual light / inscription  
**Never:** a floating task card layered over the monument

### Temporal aperture / next-event arch

**Meaning:** what is approaching in time  
**Information:** next appointment, protected opening, transition, or preparation state  
**Interaction:** enter upcoming time  
**Empty state:** spatial openness itself communicates available time  
**Never:** generic “Open time” text dropped over a busy background

### Central Aura basin / capacity vessel

**Meaning:** current capacity + Glow intelligence  
**Information:** current state and the one most relevant immediate adaptation  
**Interaction:** check in, adapt Today, Ask Glow  
**State expression:** brightness, refraction, breathing amplitude, surrounding rings, material response  
**Never:** capacity text hidden below the object or behind navigation

### Illuminated pathway

**Meaning:** temporal flow  
**States:** Now → Next → Later → Tonight → Tomorrow  
**Behavior:** brightest concentration remains around Now; past becomes residual; future softens with distance  
**Never:** paragraphs written across the path simply because it exists

### Horizon

**Meaning:** tomorrow / future possibility  
**Behavior:** distant, softer, lower-demand  
**Never:** visually louder than the present moment

The exact same implementation logic must never be copied blindly from Today into other rooms.

Each page must interpret its own approved reference according to the information that actually belongs there.

Examples:

- **Today:** present time, readiness, capacity, priorities, current action, temporal depth.

- **Beauty Command:** getting-ready orchestration across Skin → Hair → Makeup → Body → Fragrance → Final Look.

- **Skincare:** current skin state, routine mode, treatment order, compatibility, provider instructions.

- **Home:** actual rooms, furniture, shelves, drawers, bins, cleaning/maintenance zones, physical storage homes.
- **Money:** still, exact, quiet ledger-like surfaces; numbers first; restrained motion.
- **Work:** current professional situation reorganizes the room.
- **Relationships:** memories, dates, promises, shared history, boundaries, gifts, follow-up without CRM scoring.
- **Travel:** Dreaming → Deciding → Booking → Preparing → Traveling → Remembering.

- **Ideas:** incubation lifecycle.

A page fails if its interface could be copied to another Glow room with only the labels changed.

## Wording must be room-aware

Copy cannot be selected independently of the architecture.

Generic labels such as “View all,” “Open time,” “Check in,” or “Next event” may be structurally correct in data terms but still visually or semantically wrong for a room.

Wording should answer:

- what is this object?
- what is happening here?
- what is the user trying to understand or do?
- what tone fits this room?
- what can be expressed visually instead of verbally?

Use the minimum words necessary when architecture already communicates meaning.

The environment should carry part of the explanation.

## Navigation is persistent but not detached

Today, Plan, Life, Brain, and Create remain permanent and learnable.

However, persistence does not justify a generic tab bar pasted over every room.

Navigation should behave like five permanent Glow thresholds:

- same conceptual worlds
- consistent learned order
- consistent accessibility
- room-aware physical expression

Entering Plan can pull time outward. Entering Brain can deepen space. Entering Life can open surrounding habitats. Entering Create can condense mist into structure.

The navigation remains recognizable without looking visually detached from the environment.

## Top utilities must belong to the room too

Persistent utilities such as sound, replay, mode, search, or room controls must not become giant blank translucent pills floating over important scenery.

They should be:

- compact
- hierarchically clear
- spatially intentional
- physically integrated
- visually subordinate to the room's main question

Utility chrome must never steal the visual center from the page itself.

## Responsive reference fidelity

Responsive behavior does not mean shrinking desktop geometry.

For every approved reference, define device-specific compositions for:

- iPhone portrait
- iPad portrait
- iPad landscape
- desktop

The room must remain recognizably the same place on every device.

Allowed responsive changes include:

- camera reframing
- controlled crop changes
- object scale adjustments
- spatial re-layering
- moving secondary objects farther into depth
- changing how an architectural structure opens
- simplifying secondary detail
- reducing text density

Not allowed:

- abandoning the room and replacing it with cards
- turning the iPad version into a narrow desktop column
- shrinking an entire desktop scene until unreadable
- breaking information out of its architectural habitat without a device-specific spatial reason

## Accessibility without visual collapse

Accessibility must be solved inside the room language.

Requirements include:

- readable contrast
- minimum usable type sizes
- dyslexia-friendly text option
- generous invisible touch areas where needed
- keyboard/focus access
- reduced-motion behavior
- non-motion state cues
- screen-reader labels
- no meaning encoded only by color, glow, depth, or motion

Accessibility must not require replacing the approved spatial design with a generic dashboard.

## Reference permanence

Once a reference image is explicitly approved as the target for a Glow page, preserve it as that page's visual authority until the user explicitly changes or replaces it.

Future implementation work should improve fidelity to that reference rather than casually redesigning it.

**New feature ≠ new visual design.**

New functionality must be integrated into the established architecture.

When the user supplies and approves a newer reference for the same page, the newer reference supersedes the older visual target. The following do not reset:

- five-world constitution
- continuous-world behavior
- stored data
- routines and workflows
- provenance
- safety rules
- approval requirements
- undo/action receipts
- accessibility
- non-shaming behavior
- Living Glow Aura identity
- Glow Matter laws

# Final immutable standard

**The approved reference image defines the physical world. Glow understands that world and makes it operational.**

**Do not put UI on top of the world. Turn the world into the UI.**

**Information must have a natural habitat. Architecture determines where information lives.**

**Every object must have a reason before it receives data.**

**Every page must be visually specific to its approved reference and informationally specific to its purpose.**

**The live result must be almost exactly the approved image while still being real, responsive, interactive, three-dimensional, accessible, and data-driven.**

The correct end state is not concept art and not a dashboard. It is a believable living place where the architecture itself has become the operating system.
