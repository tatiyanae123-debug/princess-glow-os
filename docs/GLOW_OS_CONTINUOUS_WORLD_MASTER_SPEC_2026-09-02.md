# Glow OS — Continuous World Master Experience Layer

**Status:** Current master page-experience specification, September 2, 2026.  
**Authority:** This layer is subordinate to and compatible with the existing Glow OS constitution. It strengthens how rooms express the system. It does not erase data, workflows, provenance, safety, approval, accessibility, or the five-world foundation.

## Constitutional foundation

Glow OS is one continuous living world. Technical routes are addresses and state changes, not visual page replacements.

The five primary worlds are permanently:

1. Today
2. Plan
3. Life
4. Brain
5. Create

No Life subsystem, utility, database, or temporary workflow may become a sixth primary world.

## Shared Glow language

All rooms remain visibly part of one system through:

- Living Glow Aura as embedded intelligence, never a chatbot orb, mascot, fairy, person, or literal angel.
- Glow Matter as responsive liquid-crystal / pearl / polished-stone material behavior.
- Ivory pearl, polished stone, champagne metal, restrained water reflection, natural refraction, refined typography, and Apple-level restraint.
- Permanent Ask Glow, consistent gestures, save/undo/search/action receipts, contextual voice, and target-travel feedback.
- iPhone and iPad-first usability with desktop support.
- Reduced-motion support and dyslexia-friendly presentation controls.
- Non-shaming health, body, money, productivity, and relationship behavior.
- No false actions, silent destructive changes, or unapproved consequential rearrangements.

## The room law

Every important Glow room must be differentiated across these dimensions:

**climate → space → physics → intelligence → information → controls → completion → sound → Aura behavior**

A room is incomplete if it is merely a recolored template.

## Anti-repetition QA

Every finished screen must pass all of these questions:

- Different dominant spatial metaphor?
- Signature interaction?
- Unique light climate?
- Meaningful motion model?
- Different completion behavior?
- Distinct Glow role?
- Different information exploration?
- One primary human question?
- Navigation still feels like Glow?
- Avoids copied card structures?

## World definitions

### Today — Living Center

Today represents the present. Its spatial law is temporal depth:

**Now → Next → Later → Tonight → Tomorrow**

Now has maximum clarity. Future layers become smaller, softer, lower contrast, farther away, and less demanding. Completed time leaves warm residual light rather than becoming another checkbox grid.

Today must never regress into a conventional widget dashboard.

### Plan — Time Observatory

Plan is spatial time, not a bundle of calendar/task/project apps. Today is physically closest; tomorrow is nearby; distant time recedes. Deadlines become landmarks, projects occupy temporal territory, and Glow can project conflicts, preparation shadows, protected time, alternatives, and future-self scenarios.

Planning remains non-destructive. Glow may simulate and propose. Nothing becomes real until approved.

### Life — Personal House

Life contains lived domains, each with its own habitat and physical behavior. Beauty, Body, Fitness, Wellness, Food, Closet, Home, Money, Work, Relationships, Travel, and other domains are rooms in Life, never replacements for the five-world structure.

### Brain — Depth World

Brain must never become Notion. Notes = desk, Notes Web = constellation, Memory = cinema, Thoughts = floating holding field, Ideas = incubation, Insights = observatory, Timeline = river, Decision Archive = crossroads, and Brain Graph = universe-scale relational exploration.

### Create — Mist to Structure

Create is not a collection of AI tools. Its governing transformation is:

**vague → legible → structured → tangible**

Capture accepts input before classification. Creative Studio lets the active medium dominate. Inbox is temporary and visibly routes objects toward destinations. Import exposes source, extraction, proposed meaning, duplicate/conflict state, destination, and approval.

## Reference image authority and exactness

Any reference image the user explicitly approves or sends as the target for a Glow page becomes the authoritative visual blueprint for that page until the user replaces it.

“Match the reference” does not mean loosely inspired by it. It means preserve, as closely as technically possible:

- composition
- camera position and viewing angle
- spatial layout
- architectural forms
- object placement
- depth relationships
- material character
- lighting direction and atmosphere
- scale and proportion
- major color relationships
- negative space
- visual hierarchy
- focal points
- where information appears in the scene
- the emotional character of the room

The live page should look immediately recognizable as that reference, while remaining a functioning, responsive, accessible Glow OS interface.

Reference exactness must never be achieved by flattening the page into a screenshot. The page must remain real, interactive, responsive, data-driven, and three-dimensional in behavior.

## Semantic architecture rule

Glow does not place a conventional UI layer over a beautiful background.

For every reference image and every Glow room, first understand what each visible architectural object is doing in the world. Then assign it a semantic role.

The required order is:

**room purpose → architectural object → semantic meaning → information → interaction → state change → completion behavior**

Not:

**database field → floating card → background decoration**

Architecture determines information placement. Information is not positioned first and decorated afterward.

Examples:

- A physical sign, plaque, monument, shelf, portal, basin, mirror, rail, desk, horizon, drawer, pathway, surface, vessel, or alcove must be treated as a potential information habitat only when its form naturally supports that meaning.
- Text assigned to a physical object must live inside that object's usable visual face and respect its boundaries, perspective, curvature, lighting, material, depth, and safe padding.
- Icons and controls must feel embedded, etched, projected, illuminated, inset, suspended, or otherwise physically related to the object rather than pasted over it.
- Expanded information should emerge from, deepen, unfold, rotate, illuminate, or move through the originating object whenever possible instead of opening an unrelated generic modal.
- Completion should transform the originating object according to the room's physics rather than merely changing a checkbox.
- Decorative architecture must remain decorative when it has no useful semantic role. Glow must not fill every available surface with text.

## Reference-image semantic mapping workflow

Before implementing any page from a user-supplied reference image, create an internal semantic map of the scene.

For every meaningful object, determine:

1. What physical object is this?
2. Is it decorative, navigational, informational, interactive, atmospheric, or state-bearing?
3. What concept naturally belongs here?
4. What exact live data belongs here?
5. How much information can physically fit without damaging the reference composition?
6. What is the correct typographic plane, perspective, scale, wrapping rule, and safe boundary?
7. What happens when it is touched?
8. Where does expanded detail appear?
9. How does the object communicate hover/touch/focus without becoming generic app chrome?
10. What does completion, empty state, loading state, warning state, and disabled state look like in this object's material language?

This mapping is required before final placement of live text or controls.

## Exact reference + living 3D rule

The user wants Glow pages to be **as visually exact as possible to the approved reference photographs while still behaving like a real three-dimensional operating system**.

Therefore every approved page must satisfy both sides at once:

### Visual fidelity

The first frame should strongly match the approved photograph or image in composition, architecture, atmosphere, scale, visual balance, and object placement.

### Living functionality

The scene must remain alive:

- real text, not baked-in fake text
- real user data
- tap/click/keyboard interaction
- responsive iPhone and iPad layouts
- meaningful depth and spatial transitions
- room-specific Glow Matter response
- state changes reflected through light, material, depth, or movement
- accessible contrast and reduced-motion alternatives
- no fake controls or false actions

The goal is not a screenshot with buttons on top. The goal is for the screenshot's world to become the actual interface.

## Page-by-page specificity

The exact same implementation logic must not be copied blindly from Today into other pages.

Each page must interpret its own reference image according to the information that actually belongs there.

Examples:

- Today architecture expresses present time, capacity, priorities, next actions, and temporal depth.
- Plan architecture expresses future territory, preparation, conflicts, alternatives, and protected time.
- Makeup surfaces belong to the face, mirror, lighting, product sequence, and placement.
- Skincare surfaces belong to skin state, treatment order, compatibility, and routine mode.
- Closet information belongs to rails, drawers, folds, outfit compositions, mirrors, and garment groupings.
- Home information belongs to actual rooms, furniture, shelves, drawers, bins, maintenance zones, and stored objects.
- Money belongs to quiet ledger-like surfaces with exact numerical hierarchy.
- Notes belong to a calm writing surface.
- Memory belongs to cinematic time and resurfacing controls.
- Recipes belong to the current cooking step, ingredients needed now, attached timers, and hands-free guidance.

A page is wrong if its text could be moved unchanged onto another Glow page without losing meaning.

## Reference-image permanence

Once a reference image has been explicitly approved as the target for a specific Glow page, preserve it as that page's visual authority until the user explicitly changes or replaces it.

Future implementation work should improve fidelity to that reference rather than casually redesigning it.

New functionality must be integrated into the established architecture instead of using the new feature as a reason to replace the page's approved look.

When the user supplies a newer reference for the same page, the newer explicitly approved reference supersedes the older visual target, while constitutional Glow rules, data, safety, accessibility, and system behavior remain preserved.

## Explicit exclusions

Do not regress Glow into ordinary dashboards, identical rounded-card collections, conventional push/page-flip navigation, hard climate cuts, generic chatbot UI, Siri-like orbs, mascots/fairies/literal angels, neon/fairycore/Y2K styling, glassmorphism everywhere, repeated hero layouts, one-sidebar/database-table product models, gratuitous animation, punishment mechanics, shame-driven health/body/money indicators, silent destructive changes, false certainty, or false action receipts.

## Deepest rule

**Intelligence should feel like a natural phenomenon rather than a chatbot. Information should feel like it has a natural habitat rather than a database location.**

**The approved reference image defines the room's visual world. Glow turns that world into the functioning interface instead of placing an interface on top of it.**

A Glow screen is not finished merely because it is beautiful or functional. It must preserve the constitution, maintain continuous-world behavior, retain existing information and safety rules, possess its own room identity, honor its approved reference image, make its architecture semantically meaningful, and still unmistakably belong to Glow.
